## 1. One custody

`KistaCustody` wraps an injectable resolver callable `(service, field) -> value` (directly or by factory; built lazily — constructing the custody builds no resolver). While disabled, every resolution returns a truthful refusal as data (`ok=False`, `status="refused"`, the `error` naming custody as disabled) and touches no resolver. When enabled, a resolution parses the request's `kista://service/field` reference by the plugin's own pattern, calls the resolver with the parsed pair, and delivers the value ONLY to the caller-supplied consumer callable, in process: the response envelope files the reference, the parsed pair, the asking binding and the consumer's own result — never the value, which is stored nowhere and serialised nowhere. An enabled custody with no resolver returns the filed not-configured refusal: this module ships no live Kista client and claims none. An invalid request raises `ValueError` naming the problem(s), judged by the pure validators before any resolver is built or called. `validate_config()` judges a config mapping by the same pure validators and returns the verdict as data. Every response is a plain JSON-safe detached dict: `call`, `ok`, `status`, `contract_version` (TF-034's `API_VERSION`), `error`, plus the call's payload. No binding needs a credential today — TF-156..TF-159 each filed credential custody NOT routed / no-home — so custody here is governance plus shape: the shipped user config is migrated to references, every config in the tree is governed by the validator and the live scan, and any future need must resolve through this custody.

## 7. The rules

- `never_in_configs`: a credential value never lives in a config: the only credential-shaped thing a config may carry is a kista:// service/field reference under a *_ref key; a raw credential-shaped key in a config mapping is refused by config_mapping_problems() — empty (inert but wrongly shaped) or non-empty (a secret in a plain file) alike, D-CFG-4's fix
- `reference_never_value`: custody trades in references: parse_reference() judges a reference by the Kista plugin's own pattern exactly (service 1..128 lowercase machine chars, field 1..64), and nothing in this module files, logs or returns a credential value — values exist only as a resolver's return, in process, on their way to a consumer
- `resolved_value_never_serialised`: a resolved value is never serialised: the resolution envelope files no value field, the custody object stores no value, and the contract / as-data outputs contain none — the value reaches only the caller-supplied consumer callable; proven by the probes with a sentinel secret that appears in no serialised output
- `off_by_default`: custody is off by default: DEFAULT_ENABLED is False, filed as data (mirroring the Kista source's own enabled default False); enabling is an explicit act — the constructor flag enabled=True or the enable() method — and disable() returns custody to refusal; while disabled, every resolution returns a truthful refusal as data and touches no resolver — no resolver is built and no reference is parsed for resolution, proven by the probes with a counting factory
- `resolution_only_through_injected_resolver`: resolution happens only through an injected resolver callable (service, field) -> value: this module ships no Kista client, invokes no CLI, opens no vault and reads no key file — an enabled custody with no resolver returns the filed not-configured refusal; a live resolver is TF-170's live proof to wire, never a silent default here
- `failures_name_a_kind_never_a_value`: a failed resolution is data naming its kind (disabled / not configured / resolver refused / resolver returned nothing) — never the resolver's message, never a value, never CLI output: the Kista plugin's own discipline (failures carry no output and no reference echo beyond the caller's own reference)
- `no_binding_needs_a_credential_today`: the filed truth of this slice: no TF-153..TF-159 binding routes or needs a credential — each binding's credential custody is NOT routed / no-home in its own filings, re-derived live by the checker — so custody here is governance and shape, not a route: any future binding that needs a credential must file its need here and resolve it through this custody, never through a config
- `called_never_reimplemented`: no Kista or Hermes code is imported or copied: the plugin's shapes are filed as literal data read READ-ONLY from the Hermes tree (plugins/kista-secret-source's plugin.yaml / __init__.py / source.py) and nothing under that tree is edited by this slice; the pattern is filed as a pattern and judged by Python's re, not by Kista's code
- `every_field_has_a_disposition`: every field on either side has a FIELD_ROWS row with a disposition — none is silently dropped and none is invented; the resolved value is filed no-home in the open
- `responses_detached_json_safe_versioned`: every response is detached JSON-safe data (a JSON round-trip copy) whose contract_version is TF-034's API_VERSION, consumed from thoughtforge.cognition.api_surface — no competing version is invented here
