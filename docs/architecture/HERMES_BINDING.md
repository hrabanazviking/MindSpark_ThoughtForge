## 1. One binding

`HermesBinding` wraps TF-154's `CognitionAPI` and TF-155's `MemoryAPI` — each injectable directly, by factory, or via a `turn_callable` / `memory_store` passthrough, and both built lazily: constructing the binding builds neither API. While disabled, every routed call returns a truthful refusal as data (`ok=False`, `status="refused"`, the `error` naming the binding as disabled) and touches neither API. When enabled, a routed local turn routes through the CognitionAPI and memory calls through the MemoryAPI — called, never reimplemented. An invalid request raises `ValueError` naming the problem(s), judged by the pure validators before any API is built or called. Every response is a plain JSON-safe detached dict: `call`, `ok`, `status`, `provider_key`, `contract_version` (TF-034's `API_VERSION`), `error`, plus the call's payload (`turn` + `completion` for a provider turn, `catalog` for the catalog, `health` for health, the TF-155 response verbatim in `memory` for memory calls). No Hermes code is imported or copied anywhere: Hermes's shapes are filed below as literal data read READ-ONLY from the Hermes hack tree, and the binding performs no Hermes act — it executes no tool, sends no gateway message, holds no session or credential and decides no route. A cognition provider only, behind Hermes's own surfaces.

## 6. The rules

- `volmarr_core_real_and_named`: volmarr-core is a literal name in the Hermes tree (plugins/volmarr-core, plugin.yaml manifest_version 2, name volmarr-core, version 0.26.0): the binding is shaped on the plugin surfaces that tree actually files — its cognition attachment, its routing schema, the model-provider and memory-provider plugin surfaces — and invents no Hermes API; where this slice's brief said 'if volmarr-core does not exist as a literal name, say so', the measured truth is that it does exist, filed here with its evidence
- `composition_boundary_holds`: the composition boundary holds (ARCHITECTURE_VOLMARR.md): Hermes core stays a narrow waist and the shell owns turns, sessions, provider resolution, tools and gateways; the binding is an external cognition provider BEHIND those surfaces — it patches no Hermes core or facade, registers nothing itself, decides no route, resolves no provider and owns no Hermes domain's state
- `off_by_default`: the binding is off by default: DEFAULT_ENABLED is False, filed as data; enabling is an explicit act — the constructor flag enabled=True or the enable() method — and disable() returns the binding to refusal; while disabled, every routed call returns a truthful refusal as data (ok=False, status="refused", an error naming the binding as disabled) and touches neither API — no API is built and no call is routed, proven by the probes with counting factories
- `called_never_reimplemented`: cognition routes only through TF-154's CognitionAPI and memory only through TF-155's MemoryAPI (which itself calls TF-057's toolset) — this module implements no cognition, store or enforcement logic of its own, and no Hermes provider, router or manager logic either
- `no_hermes_code_imported_or_copied`: no Hermes code is imported or copied: Hermes's shapes are filed as literal data read READ-ONLY from the Hermes hack tree (plugins/volmarr-core's plugin.yaml / cognition.py / routing.py / context_packet.py, plugins/model-providers, agent/memory_provider.py, plugins/context_engine), and nothing under the Hermes tree is edited by this slice; no credential — above all no endpoint key — is ever filed, passed or stored by the binding (TF-160 owns credential custody)
- `every_field_has_a_disposition`: every field on either side has a FIELD_ROWS row with a disposition — none is silently dropped and none is invented; max_tokens and any credential are filed no-home in the open
- `responses_detached_json_safe_versioned`: every response is detached JSON-safe data (a JSON round-trip copy) whose contract_version is TF-034's API_VERSION, consumed from thoughtforge.cognition.api_surface — no competing version is invented here
